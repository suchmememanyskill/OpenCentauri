# Centauri Carbon MCU Identifier

A diagnostic tool written in Rust to identify variants of the STM32-based toolhead boards used in Centauri Carbon firmware (v1.4.44 and similar).

## Overview

This tool communicates with the Klipper-based firmware on the toolhead MCU via a serial port. It uses specific heuristics derived from the reverse engineering of the `app` binary (v1.4.44) to distinguish between the **Original (Lite)** toolhead board and the **New** toolhead board (which features integrated Hall Effect and Filament Runout sensors).

## Identification Heuristics

The tool identifies the hardware variant by triggering a "data dictionary" dump from the MCU and scanning for the following identifiers:

| Identifier | Hardware Variant | Rationale |
| :--- | :--- | :--- |
| `lis2dw` | **New Board** | The new board uses the LIS2DW12 accelerometer instead of the ADXL345. |
| `HallFilamentWidthSensor` | **New Board** | Confirms the presence of the integrated Hall effect filament sensor. |
| `QUERY_FILAMENT_SENSOR` | **New Board** | Indicates the toolhead-based `RunoutHelper` is active (commands handled by STM32). |
| `adxl345` | **Old/Lite Board** | The original board variant uses the ADXL345 accelerometer. |

## Technical References (Reverse Engineering Context)

For reverse engineers looking to verify or extend this logic, the following locations in the Centauri Carbon workspace are relevant:

### 1. MCU Connect & Constant Checking
*   **Original Source:** `core/klippy/mcu.cpp` (around line 441 in constructor/connect logic).
*   **Decompiled Pseudo-C:** `stock/app-1.4.44.pseudo_c.txt` at offset **`00065040`**.
    *   Logic: `if (*(*(arg1 + 4) + 0x6c) == 0x10)` checks if `pins_per_bank == 16` (Lite variant).
*   **HLIL:** `stock/app-1.4.44.hlil.txt` at line **74146**.

### 2. Accelerometer Probing
*   **Decompiled Pseudo-C:** `stock/app-1.4.44.pseudo_c.txt` at offset **`0023db30`**.
    *   Logic: Switches between `config_adxl345` and `config_lis2dw` based on `adxl_type`.
*   **SPI Probe:** `sub_2419a0` (HLIL) sends specific probe headers (`0xA8`, `0xAF`) to determine which sensor is physically present.

### 3. Filament Detection
*   **Old Board:** Handled by mainboard R528 GPIO **GPIOC(0)** (`0x40`). Reference: `devices/gpio.h`.
*   **New Board:** Handled via `RunoutHelper` object on the STM32. Reference: `core/klippy/extras/hall_filament_width_sensor.cpp` (which instantiates the helper).

## Usage

### Prerequisites
*   Rust toolchain (`cargo`, `rustc`).
*   `cross` and Docker for the default ARMv7 build script.

### Building
```bash
cd mcu-identifier
./compile.sh
```

### Running
To identify an MCU on `/dev/ttyACM0` at `250000` baud:
```bash
./target/armv7-unknown-linux-musleabihf/release/mcu-identifier /dev/ttyACM0 250000
```

## Protocol Details
The tool sends a sequence of `0x7e` (Klipper SYNC bytes) to the serial port. This forces the MCU to restart its internal parser and re-transmit its configuration constants and command dictionary, which are then parsed by this tool's heuristics.

## Kalico Firmware Compatibility

This tool is compatible with both standard **Klipper** and its offshoot, **Kalico**.

### Why it works:
*   **Protocol Heritage**: Kalico maintains the core Klipper binary protocol and framing (0x7e SYNC).
*   **Hardware-Bound Identifiers**: The heuristics (e.g., `lis2dw`, `HallFilamentWidthSensor`) are based on strings generated by the MCU firmware to describe physical peripherals. Unless these modules are explicitly renamed in a firmware fork, they remain the definitive "tells" for specific hardware variants.
*   **Xterra/Kalico Context**: This tool's logic is specifically aligned with the 1.4.44 firmware, which represents the transition towards the Kalico/Centauri Carbon ecosystem and the newer toolhead hardware.

## Debugging Unknown Variants

If the tool reports a board as **"Unknown"**, you can capture the raw data dictionary from the MCU to inspect it for new identifiers:

1.  **Capture a dump**:
    ```bash
    ./target/armv7-unknown-linux-musleabihf/release/mcu-identifier /dev/ttyACM0 250000 > dictionary_dump.bin
    ```
2.  **Inspect for strings**:
    ```bash
    strings dictionary_dump.bin | grep -iE "sensor|adc|config"
    ```
    New identifiers found here can be added to the matching logic in `src/main.rs`.
